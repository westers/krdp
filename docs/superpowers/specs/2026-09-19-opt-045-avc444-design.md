# OPT-045 — AVC444 (H.264 4:4:4 over RDPGFX) for the KRDP fork (design)

Status: approved section by section in conversation with Steve, 2026-09-19. Written form.
Tracker: `~/dev/krdp/research.md` OPT-045. Related: OPT-016 (adaptive quality), OPT-035 (keyframe on
demand), OPT-046 (private HEVC/AV1, later), and the virtual-output repaint spike (separate, in progress).
Repos: server `~/dev/krdp` (`master`) + private KPipeWire `~/dev/kpipewire` (`westers/opt-015`,
patches exported to `~/dev/rdp/kpipewire-vaapi-fix/patches-6.6.4/`); a small client task in
`~/dev/krdp-client` (`main`).

## 1. Purpose

Small coloured text and UI chroma smear under AVC420 because H.264 4:2:0 halves the chroma resolution
both ways. MS-RDPEGFX's AVC444 (and AVC444v2) carries full 4:4:4 chroma as **two** H.264 4:2:0 streams
per frame — the normal "main" stream plus an **auxiliary** stream whose planes hold the chroma samples
4:2:0 threw away. Every current client decodes it (FreeRDP ≥ 2, Remmina, mstsc). The fork's earlier
attempt (removed 2026-09-15) wrapped a single stream in the AVC444 envelope and was AVC420 with a
different label; this design is the real two-stream implementation.

Decisions taken with Steve:

- **When:** whenever the client advertises AVC444 caps — Remmina, the own client, mstsc — default on,
  with a config override. No `KRDPCTL` involvement.
- **Under congestion:** the auxiliary chroma stream is the **first** thing shed (luma-only frames, i.e.
  AVC420 quality) and the last thing restored; QP steps come after. Per frame, no session-level fallback.
- **Frame path:** **approach A** — the CPU split with runtime-dispatched SIMD (AVX-512 on hal9000's
  Zen 4, AVX2 elsewhere, FreeRDP's SSE4.1 primitive as the fallback), two `h264_vaapi` encodes per
  frame. The split is one unit with a fixed interface so a GPU split (approach B) can replace it later
  without touching the RDP side. Steve wants the fully GPU path (GPU split here, GPU decode in the own
  client) as a follow-on together with OPT-046.
- Ubuntu's libfreerdp 3.31 ships YUV primitives up to SSE4.1 only (no AVX2/AVX-512 for the split) —
  hence our own kernels. buzz (the client) has no AVX-512; irrelevant: the split runs on the server.

## 2. Requirements

R1. Negotiate per connection from the RDPGFX caps: AVC444v2 if advertised, else AVC444, else AVC420
    (today's path, byte-for-byte). Config `Codec=auto|avc420|avc444` (default `auto`).
R2. Two-stream encode: main 4:2:0 + auxiliary chroma 4:2:0, both `h264_vaapi` on the 780M, same
    QP/GOP, keyframe requests fan out to both; `RGB → (main, aux)` by `Avc444Split` with bit-exact
    scalar / SSE4.1-FreeRDP / AVX2 / AVX-512 variants, chosen at runtime.
R3. Wire: `RDPGFX_WIRE_TO_SURFACE_PDU_1` with the negotiated codec id and an
    `RDPGFX_AVC444_BITMAP_STREAM` — `LC=0` (both streams) or `LC=1` (luma only); never `LC=2`; one
    metablock per stream.
R4. Keyframe rules hold for the pair: surface reset → IDR on both; first aux frame after a luma-only
    stretch is an aux IDR; the OPT-035 send-queue rule applies to the pair.
R5. Adaptive quality gains one rung above today's QP ladder: shed chroma first, restore it last; logged.
R6. Observability: negotiated codec in the server startup/connection lines and in the own client's
    summary; `krdpplasmastreamer --codec avc444` writes `main.raw` + `aux.raw`.
R7. AVC420 clients and `Codec=avc420` behave exactly as today (regression guard: byte-identical PDUs).
R8. Cost is measured, not assumed: per-frame download + split time and per-frame encode time at
    2560x1440 are logged (debug) and reported in the acceptance.

## 3. Negotiation and configuration (server: `src/RdpConnection.cpp`, `src/VideoStream.cpp`)

- `FreeRDP_GfxAVC444` / `FreeRDP_GfxAVC444v2` are set true again on the server settings (they gate what
  the server advertises). On `onCapsAdvertise` the caps set is selected as today (highest version with
  AVC420 enabled and `RDPGFX_CAPS_FLAG_AVC_DISABLED` clear); the codec follows MS-RDPEGFX's table for
  that version: caps ≥ 10.1 → `AVC444v2`, caps 10.0 → `AVC444`, older → `AVC420` (the implementer
  verifies the exact version→codec mapping against MS-RDPEGFX §2.2.3.5–3.7 and FreeRDP's
  `rdpgfx_main.c` client side; the mapping is a table in `VideoCodecSupport.h`, unit-tested).
- New kcfg key `Codec` (`String`, default `auto`): `avc420` forces AVC420 regardless of caps; `avc444`
  behaves like `auto` but logs a warning when the client cannot do it. The server never writes config.
- Logging: startup summary gains `codec=<config value>`; the per-connection line after caps gains
  `codec=avc444v2|avc444|avc420`. `VideoStream` exposes `negotiatedCodec()` for the summary and tests.

## 4. Encoder pipeline (private KPipeWire)

### 4.1 `Avc444Split` (new, `src/avc444split.{h,cpp}` in KPipeWire)

```
struct Avc444Planes { I420 main; I420 aux; };            // I420 = Y,U,V planes + strides
void split(const uint8_t *bgra, int stride, int w, int h, Avc444Planes &out, Variant v = Variant::Auto);
Variant best();                                          // runtime choice
```

- Layout per MS-RDPEGFX 3.3.8.3.2/3 (what FreeRDP's `RGBToAVC444YUV` / `RGBToAVC444YUVv2` produce for
  version 1 / 2): main = full-res Y + 2×2-subsampled U/V; aux = the remaining chroma samples arranged as
  a 4:2:0 frame of the same dimensions. Version 1 and 2 differ in the aux arrangement; both provided.
- Colour matrix: BT.709 limited range — the one FreeRDP's decoder inverts.
- Variants: `Scalar` (reference), `FreeRdp` (calls `primitives_get()->RGBToAVC444YUV[v2]`, SSE4.1 on
  Ubuntu's build), `Avx2` (`__attribute__((target("avx2")))`), `Avx512`
  (`target("avx512f,avx512bw,avx512vl,avx512vbmi")`); `best()` uses `__builtin_cpu_supports` in the
  order Avx512 → Avx2 → FreeRdp → Scalar. `KPIPEWIRE_AVC444_SPLIT=scalar|freerdp|avx2|avx512` forces
  one (tests and measurement).
- Unit test `Avc444SplitTest`: random frames (odd sizes included), all available variants bit-exact
  against `Scalar`; a fixed vector compared against FreeRDP's primitive to pin the layout; a timing
  print per variant at 2560x1440.

### 4.2 Frame path and encoders (`pipewireproduce.cpp`, `h264vaapiencoder.cpp`, `encoder.cpp`)

- `PipeWireBaseEncodedStream` gains `setChromaMode(ChromaMode::Yuv420 | Yuv444)` (default 420) and a
  per-frame `setAuxStreamEnabled(bool)` (the congestion switch; default true in 444 mode).
- In 444 mode the produce thread downloads the frame to CPU (the existing dma-buf → CPU path used by the
  software encoders), runs `Avc444Split::split`, and feeds **two** `H264VAAPIEncoder` instances (main,
  aux) through the existing software→VA upload path. Both share quality/QP (the OPT-016 reopen applies to
  both), GOP, and keyframe requests (`requestKeyFrame()` fans out). Aux encoder idle while the aux stream
  is disabled; on re-enable it is asked for an IDR before its first packet is emitted (R4).
- Packets are paired by frame timestamp into `PipeWireEncodedStream::Packet` gaining
  `aux()` (`QByteArray`, empty when luma-only) and `auxIsKey()`. Ordering: a pair is emitted only when
  both encoders returned (or the aux is disabled); a straggler is dropped with a debug line — never
  emitted out of order.
- Timing: `kpipewire_record` debug category logs download µs, split µs (and variant), main/aux encode µs
  per frame (rate-limited to one line per second with min/avg/max) — R8.

## 5. Wire path and adaptive rule (server `src/VideoStream.cpp`, `src/AdaptiveQuality.h`)

- `sendFrame()` for a 444 connection builds `RDPGFX_AVC444_BITMAP_STREAM{cbAvc420EncodedBitstream1 =
  main size, LC = aux.isEmpty() ? 1 : 0, bitstream[0] = {meta, main}, bitstream[1] = {auxMeta, aux}}` and
  the surface command with `codecId = RDPGFX_CODECID_AVC444v2|AVC444`; metablocks as today's AVC420 one
  (surface rect, one quant entry with the current QP). `rdpgfx_write_h264_avc444` (FreeRDP server API)
  does the serialisation.
- Keyframes: `performReset()` (surface recreated) → `requestKeyFrame()` → both encoders; the "request an
  IDR when the first frame after a reset is not a keyframe" rule checks `isKey && (aux.isEmpty() ||
  auxIsKey)`. After a luma-only stretch the produce side guarantees the aux IDR (4.2).
- Adaptive quality: `KRdp::AdaptiveQuality::step()` gains the chroma rung as level 0 above the QP ladder:
  a step-down from the top state disables the aux stream (`setAuxStreamEnabled(false)`) and keeps QP;
  further step-downs lower QP as today; step-ups raise QP first and re-enable chroma last (after the
  hold). Unit test covers the ordering. Log: the existing adaptive line gains `chroma=on|off`.
- AVC420 connections: the code path is untouched (R7); a unit test asserts the AVC420 PDU bytes are
  identical to the current implementation for a sample frame.

## 9. Amendments 2026-09-19 (after planning; binding over §4.2, §5 and R3/R4 where they differ)

Found while reviewing the implementation plans and measured on the 780M (`h264_vaapi`, radeonsi, Mesa
26.0.8, FFmpeg 8): FreeRDP's client decodes both AVC444 bitstreams through **one** H.264 decoder
(`avc444_decompress` → the same `H264_CONTEXT` for stream 1 and stream 2), so the two pictures of a
frame must form one coherent H.264 stream — two independent encoders (§4.2 as written) would give the
client's decoder wrong references. At the same time radeonsi offers **one** reference per P picture
(`supported references: 1 / 1`), so interleaving main and aux pictures in one encoder context makes every
main P predict from the aux picture: measured 100 B → 74 227 B per main P (= I-frame size) on a
desktop-like sequence. Neither shape works; the design is therefore:

- **A9.1 Two contexts, one stream.** The main picture goes through the existing `H264VAAPIEncoder`
  context (its P chain never sees an aux picture — the luma stream costs what AVC420 costs). The aux
  picture goes through a second, intra-only `h264_vaapi` context, and each aux access unit is rewritten
  (`Avc444NalRewriter`, pure, unit-tested and decode-round-trip-tested with libavcodec's software decoder)
  into a **non-reference, non-IDR I picture** valid under the main stream's SPS: `nal_ref_idc 0`,
  `nal_unit_type 1`, `frame_num = main frame_num + 1 (mod MaxFrameNum)`, `idr_pic_id` and
  `dec_ref_pic_marking` dropped, aux PPS renumbered to id 1 and sent inline, aux SPS/SEI dropped, CABAC
  re-aligned, emulation prevention re-applied. `pic_order_cnt_type` 2 (what `h264_vaapi` emits) gives the
  non-reference picture POC `2·frame_num − 1` by itself; type 0 is written explicitly; type 1 is refused.
  Precondition: the aux SPS's parse-relevant fields equal the main SPS's, else the session falls back to
  4:2:0 with a warning. POC type 2 forbids two consecutive non-reference pictures: never two aux pictures
  without a main between them.
- **A9.2 Aux policy.** With chroma enabled, the aux is sent with a frame when the gap since the previous
  encoded frame is ≥ 100 ms or the main is a keyframe; during faster motion frames are luma-only
  (`LC = 1`). **At-rest refresh:** 150 ms after a luma-only frame with no new frame, one aux-only packet
  is emitted for the last frame and sent as **`LC = 2`** (chroma-only; R3's "never `LC = 2`" is
  withdrawn — `LC = 2` is exactly this refresh). Both constants are env-tunable for acceptance and
  recorded in research.md with the measured costs. The congestion rung (§5) suppresses both; when it
  restores chroma, the next frame or refresh carries the aux.
- **A9.3 Keyframes.** R4 simplifies: the aux is always intra, so "aux IDR after a luma-only stretch" is
  automatic; the surface-reset/IDR rules apply to the main picture; the send-queue keyframe-supersedes
  rule drops main+aux pairs as units and may drop aux-only packets freely.
- **A9.4 Geometry.** Both pictures are W × H (the coded size is the main SPS's). For AVC444 **v1** this
  means the bottom `H mod 16` odd chroma rows cannot be carried when H is not a multiple of 16 (v2 is
  height-exact and is what every FreeRDP ≥ 2 and mstsc negotiate) — documented, not worked around.
- **A9.5 Acceptance adds** per-picture byte counts (main P with/without chroma, aux) and the
  one-decoder round trip of an interleaved stream (`ctest` on hal9000) as the first test of the rewriter.

## 10. Follow-up 2026-09-20 — chroma policy tunable from the own client (OPT-045b)

Found in Steve's first live session: on a monitor with a perpetual animation (Chrome at ~40 fps on
DP-1) the inter-frame gap never reaches `motionGap` and the desk never rests, and the periodic IDRs
are not predictable by the encoder, so the aux picture was never sent — that monitor stayed 4:2:0 for
the whole session while the other one got its chroma. Steve's rulings: add a maximum interval; make
the policy a server default that the own client can override, exposed as an **advanced** setting.

- **A10.1 New rule `maxGap`** (default 1500 ms): when no aux picture has gone out for `maxGap`, the
  next frame carries one regardless of motion (an intra aux, ~40–60 KB, i.e. ≈ 0.3 Mbit/s at 1080p per
  busy monitor). The timing line gains an `aux max-gap N` count. The other rules are unchanged;
  the congestion rung still suppresses everything.
- **A10.2 Server defaults** in `krdpserverrc`: `Avc444MotionGapMs` (100), `Avc444RestMs` (150),
  `Avc444MaxGapMs` (1500), read at start and on runtime reload for the next connection; the
  `KPIPEWIRE_AVC444_*` env vars remain KPipeWire-level debug overrides used only when the server
  passes nothing. Startup summary gains `chroma=motion/rest/max`.
- **A10.3 KPipeWire API**: `PipeWireBaseEncodedStream::setChromaPolicy(ChromaPolicy{motionGapMs,
  restMs, maxGapMs})` (queued to the produce thread → `Encoder::chromaPolicyChanged()`); applied
  live by `H264VAAPIAvc444Encoder` (atomics); validation: each in [16, 5000] and
  `motionGap ≤ rest ≤ maxGap`, else the call is refused with a warning and the previous policy stays.
- **A10.4 `KRDPCTL` message `chroma`** (own client → server, `v:1`):
  `{"v":1,"type":"chroma","motionGapMs":100,"restMs":150,"maxGapMs":1500}` — every field optional;
  a missing field keeps the server default; the server validates as in A10.3, applies to that
  connection's sessions only (persisting for the connection, later `chroma` messages override), logs
  `chroma policy: motionGap=… rest=… maxGap=… (client)`, and answers an `error` with code `invalid`
  when a value is out of range (nothing applied). Channel-less clients keep the server defaults.
- **A10.5 Client**: Settings → new **Advanced** group: "Chroma detail timing (ms)" — three fields
  Motion gap / Rest / Max gap, blank = server default; and "Prefer AVC420 (no full-colour chroma)"
  (the client stops advertising AVC444/v2 — for A/B by eye). Global to the client (per-connection
  later if wanted). Sent as `chroma` right after the channel is up (after the `takeover`/first `layout`
  exchange), and again when changed while connected. Debug actions `chroma=<motion>,<rest>,<max>` (`-`
  keeps a field unset) and `prefer-avc420=0|1`; the debug summary shows `chromaPolicy=…` when sent.
  Client 0.4.2.
- **A10.6 Acceptance**: headless from buzz: `chroma=100,150,1500` → the server line; on the busy DP-1
  the timing line shows `aux max-gap ≥ 1` within 2 s and the client's `chromaFrames` grows while
  `skipped-motion` stays high; `chroma=5000,100,100` → `error invalid`, nothing applied;
  `prefer-avc420=1` → `codec=avc420`; a third-party client unchanged.
